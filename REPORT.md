# Design Report

## Architecture

The system is a focused single-process vertical slice with separate modules for page observation, LLM planning, policy enforcement, artifact compilation, deterministic replay, evidence logging, validation, and human intervention.

The local application in `src/app/server.js` represents a legacy banking interface with server-rendered pages, table-based layout, no test IDs, and runtime business outcomes. It provides a safe and repeatable substitute for a real banking application.

During discovery, Playwright opens the target application and `observePage` converts the current interface into a compact representation containing the URL, title, visible text, and interactive controls. The planner sends the natural-language goal, observation, and previous decisions to the OpenAI Responses API. Structured Outputs constrain every model response to one supported action and prevent free-form instructions from reaching the executor.

The discovery loop follows a bounded observe, decide, and act sequence. Policy checks every model-selected action before Playwright executes it. A successful action history is passed to the compiler, which produces a parameterized capability artifact. The raw model interaction is retained only as sanitized evidence and is not used as the production program.

The replay engine is a separate execution path. It loads an artifact, validates it against JSON Schema, validates invocation inputs, enforces approval and safety policy, executes the declared steps, checks postconditions, verifies the final checkpoint, and extracts typed outputs. Replay does not import the OpenAI SDK and continues to work after the API key is removed from the active environment.

A single process was chosen to keep the implementation understandable and to preserve the same live Playwright session during human intervention. A production system would separate orchestration, browser workers, artifact storage, policy decisions, and operator routing, but building that infrastructure would not improve the core design demonstrated here.

## Artifact schema

The artifact is designed as an agent-invocable contract rather than a raw browser recording. It includes a stable capability ID, schema version, semantic capability version, title, description, approval state, target entry point, typed inputs, typed outputs, ordered actions, postconditions, a final checkpoint, expected business outcomes, locator strategy, and sanitized provenance.

`schemaVersion` controls compatibility between the artifact and interpreter. The capability `version` tracks behavioral changes to an individual automation. These concerns are separate because the artifact format can remain unchanged while the behavior of one capability evolves.

Inputs and outputs are explicitly declared. `memberId` is a required five-digit string and is marked sensitive. `balance` is declared as a numeric output with a currency transformation. This gives a calling agent a clear contract and allows replay to reject malformed inputs before operating the application.

The compiler converts the concrete discovery value into `{{memberId}}`. The discovered value is never stored as a step value. Model explanations and provenance are also sanitized so concrete member identifiers cannot enter the artifact indirectly.

Each action includes an action type, semantic target, and risk classification. Accessibility role and accessible name are preferred over DOM paths because they describe the control’s purpose and transfer more naturally to accessibility-based desktop automation. Scoped CSS is supported as a fallback for output extraction.

Postconditions verify individual steps, while the final checkpoint verifies the complete capability. This prevents replay from assuming that a click succeeded merely because Playwright completed the click operation.

Artifacts generated by discovery begin as `draft`. A human must review and change the state to `approved` before unattended replay. JSON Schema validation and automated tests prevent malformed or unsupported actions from entering execution.

## Determinism & error handling

Deterministic replay means the model is not asked to choose any production action. Replay reads the same ordered steps, targets, parameters, postconditions, checkpoint, and output definitions from the approved artifact on every invocation.

Runtime inputs are substituted only during execution. The replay engine supports semantic role-and-name targeting and scoped CSS fallback. Playwright provides actionability checks and automatic waiting for controls to become visible, stable, enabled, and actionable. The artifact also supports an explicit wait action for known loading states.

The result contract separates expected business outcomes from technical failures. `MEMBER_NOT_FOUND` is returned as `business_outcome` because the application operated correctly and produced a legitimate domain result. It is not reported as an exception.

Unexpected conditions are returned as `failure`. Failure results contain the error category, error message, failing step index, failing step ID, and current URL. A screenshot and structured event log preserve the state needed for debugging. The submitted evidence includes a timeout caused by a deliberately missing button.

Every action can declare a postcondition. If a postcondition fails, replay first checks whether the page matches a declared business outcome. If it does not, replay stops rather than continuing blindly. The final checkpoint must pass before any output is returned.

Recoverable behavior is intentionally conservative. Playwright handles ordinary page slowness through bounded actionability waits. The `wait` action provides an explicit mechanism for known loading states. A production artifact format should add declared retry budgets, known-dialog handlers, session-renewal workflows, and idempotency requirements. A generic retry loop was avoided because retrying financial actions without knowing their side effects can duplicate an irreversible operation.

## Heterogeneity & multi-tenant

The implementation targets a browser, but the artifact uses semantic actions and targets rather than Playwright-specific objects. The boundary between perception and execution is represented by the observer, target conversion, and action-execution functions.

A legacy-web adapter could extend this boundary with frame traversal, table interpretation, OCR anchors, screenshot regions, and coordinate-based fallbacks. A desktop adapter could implement the same semantic operations using Windows UI Automation, macOS Accessibility, or an OS-level computer-use driver. Coordinate targets should include a reference resolution, stable visual anchor, bounded region, and confidence threshold so weaker targeting remains explicit and reviewable.

The preferred targeting order would be accessibility role and name, stable application metadata, anchored visual targeting, and finally raw coordinates. A capability should identify which strategy each step uses so reviewers understand its reliability.

For multi-tenant reuse, capabilities should belong to a vendor-application family rather than directly to one institution. A base capability would declare the vendor family and supported application-version range. Tenant configurations would provide entry points, branding-dependent names, and small locator overrides without duplicating the entire flow.

Replay telemetry should be grouped by capability version, vendor version, and tenant variant. A capability should be promoted only after passing a replay matrix against representative versions. Repeated failures across one vendor version would indicate application drift. Repeated tenant-specific overrides would indicate that a separate base variant is needed.

The current vertical slice does not implement tenant storage or desktop control. It keeps the artifact independent of raw Playwright selectors so those capabilities can be added without replacing the core contract.

## Escalation & handoff

The system escalates when policy identifies an irreversible action requiring human approval. The automation pauses before executing the action and retains the same Playwright browser, page, cookies, navigation state, and entered form values.

Before transferring control, the handoff module records the capability step, reason, current URL, control owner, and a screenshot. The terminal tells the operator which step stopped and why. The operator then interacts directly with the same visible browser session.

After completing the manual action, the operator returns to the terminal and signals resume. The system captures an after-handoff screenshot, records the manual action, transfers ownership back to automation, and evaluates the original step postcondition. Automation continues only if the page reached the state required by the artifact.

Evidence records `control_transferred_to_human`, `human_action_completed`, `control_returned_to_automation`, and the final replay result. This makes ownership transitions auditable.

The demonstration uses a terminal-based operator surface to keep the handoff mechanism real but small. A production design would use an authenticated browser-streaming console, operator identity, reason codes, control leases, timeouts, durable intervention queues, and role-based authorization. A lease would ensure that automation and a human cannot control the session simultaneously.

## Safety

The safety model treats artifacts and model decisions as untrusted input. Navigation is restricted to configured origins and route prefixes. Action types are allowlisted. Capability length is bounded. Discovery and replay use the same action policy.

Every action includes a risk classification. Reversible actions may execute automatically. Irreversible actions trigger human intervention. Newly discovered artifacts are drafts and cannot execute through the unattended replay path until reviewed and approved.

Formal JSON Schema validation runs before replay. Unknown action types, malformed versions, missing contracts, and unsupported structures are rejected before the browser opens. Invocation inputs are validated separately so artifact errors, caller errors, and policy denials remain distinguishable.

The API key is read from an environment variable and is never placed in source code. `.gitignore` excludes environment files and dependencies. API responses are not stored by the provider when the request supports `store: false`.

Structured logs recursively redact member identifiers, SSNs, long account-number patterns, tokens, passwords, and secret-like values. Financial outputs and form-entry values are deliberately replaced before persistence. URLs are sanitized because query parameters can contain identifiers. Screenshots use only fictional local data.

Regex redaction is not sufficient for a production financial system. Production should add field-aware data classification, screenshot OCR redaction, encrypted evidence storage, strict retention limits, tenant-specific encryption keys, secret-broker integration, audit access controls, and automated leak scanning before evidence becomes available to operators.

## Cuts

The project deliberately implements a complete vertical slice instead of production-scale infrastructure.

The operator interface is terminal-based rather than a real-time co-browsing console. The control-transfer mechanism, same-session behavior, ownership events, screenshots, and resume signal are real.

Only a web surface is implemented. Legacy-web and desktop adapters are described but not built. The current observer uses visible text and semantic controls rather than screenshots or OCR. This is sufficient for the chosen proxy application while keeping the adapter boundary clear.

Artifact compilation is specialized to the demonstrated member-balance capability. A general compiler would infer parameters, outputs, checkpoints, business outcomes, and reusable locator candidates from multiple successful traces and human annotations.

Artifacts and evidence use local files. A production system would use signed artifacts, versioned object storage, a capability registry, approval workflows, durable browser workers, encrypted session profiles, queues, and tenant isolation.

Recoverable conditions currently rely on bounded Playwright waiting and explicit wait actions. The next extension would add artifact-declared recovery policies with retry limits, idempotency classification, known-dialog handlers, and session-timeout recovery.

Additional high-value next steps would include a second tenant variant, measured replay stability across repeated runs, approval based on a replay threshold, screenshot redaction, and a small agent-facing capability catalog.
